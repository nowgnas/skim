# 로컬 데이터 보관과 삭제 주기 설계

## 목표
사용자가 데이터 위치와 보관 상태를 이해하고, PR 데이터의 보관 기간 및 정리 실행 주기를 설정한다. DB 파일 전체를 주기적으로 삭제하지 않는다. 실행 중 분석·수집과 충돌하지 않고, 백업에 남는 별도 사본의 보관 범위를 표시한다.

## 현재 저장 경로와 상태
- 기본 설정: `~/.config/skim/config.json`. 기본 데이터 루트: `~/.local/share/skim/`. `SKIM_HOME`이 있으면 각각 `$SKIM_HOME/config/`, `$SKIM_HOME/data/`다 (`lib/skim/config.py`). 실제 실행 서비스가 쓰는 환경이 기준이다.
- SQLite `skim.db`: 저장소·PR 정보와 본문, 스냅샷 메타데이터, 분석, 작업 기록, 정책과 호출 예산. WAL 모드의 `skim.db-wal`, `skim.db-shm`이 생길 수 있다 (`lib/skim/db.py`).
- 원본 diff: `cache/diffs/<hash>.diff`. 참조가 없어진 diff는 수집 후 정리한다 (`lib/skim/collect.py`).
- DB 마이그레이션 백업: `skim.db.v<version>.<timestamp>.bak`. 업데이트 백업: `update-backups/<update-id>.sqlite`. 백업은 정리된 DB의 이전 사본을 포함할 수 있다 (`lib/skim/db.py`, `lib/skim/update_backup.py`).
- 분석 실패 진단: `logs/analysis.log`에 단계와 제한된 예외 유형이 기록될 수 있다. 1 MiB 초과 시 추가 기록을 중단하는 구현이다 (`lib/skim/analyze/__init__.py`).
- 현재 `retention_days`의 기본값은 30이지만 자동 보존 기간 삭제에는 사용하지 않는다. 제거 시 기본은 데이터 보존이고 `skim uninstall --purge-data`는 전체 데이터를 삭제한다.

## 정책 제안
| 대상 | 추천 기본값 | 시작 기준 | 정리 대상 |
|---|---|---|---|
| PR 상세·스냅샷·분석 | 7일 | GitHub가 확인해 준 종료/머지 시각 | 만료된 PR의 제목·본문 포함 로컬 PR 레코드와 종속 스냅샷·분석 |
| 원본 diff | PR과 동일 | 마지막 참조 제거 시 | 어떤 스냅샷에서도 참조하지 않는 파일만 |
| 완료된 작업 기록 | 90일 | 작업 종료 시각 | 완료·실패·취소 등 종료된 기록. 대기·실행은 보존 |
| 업데이트·마이그레이션 백업 | 별도 정책, 기본 보존 | 백업 생성 시각 | 진행 중 업데이트·복구에 필요한 백업은 절대 제외. 자동 삭제를 기본값으로 하지 않고 화면에 개수·용량과 별도 삭제를 제공 |
| 로그 | 30일 또는 용량 상한 | 파일 생성·수정 시간 | analysis.log의 마지막 기록 후 설정 기간이 지나면 파일 정리. 계속 기록 중이면 오래된 항목도 남음 |
| 설정·등록 저장소·인증 링크·예산 | 유지 | 해당 없음 | 기간 만료 자동 삭제에서 제외 |

기본 정리 주기는 12시간이며 서버가 실행 중일 때만 실행한다. 앱이 꺼져 있었다면 시작 후 한 번 점검한다. 저장 시 즉시 삭제하지 않고 다음 주기에 반영한다. 닫힌 시각을 모르는 기존 PR은 자동 삭제하지 않으며 GitHub에서 확인 가능한 경우에만 시각을 채운다. 다시 열린 PR이나 접근 불가·조회 실패 등 최신 상태를 확인할 수 없는 PR은 삭제를 보류한다. GitHub 확인 요청은 대상만 대상으로 하며 실패는 다음 주기에 재시도한다.

## 설정 UX
- 설정 > 데이터 보관: 현재 실제 경로, DB·diff·백업·로그의 크기, 최근 정리 결과 및 다음 예정 시각.
- PR 보관 기간: 7·30·90·180일과 직접 입력, 정리 끄기. 기본값은 7일. 작업 기록과 로그 보관은 고급 설정에 배치.
- 정리 실행 주기: 6·12·24시간, 기본 12시간. 보관 기간과 실행 간격을 별도 개념으로 설명한다.
- `지금 정리` 전 대상 건수와 예상 크기를 조회하고, 실제 삭제는 확인 후 실행한다. 화면에서 GitHub 삭제는 발생하지 않음을 명시한다.
- 백업은 복구 가능성과 개인 코드 잔존을 함께 설명하고, 개별 삭제는 별도 확인한다. 진행 중 업데이트·복구 백업은 삭제할 수 없다.
- 선택된 설정은 CLI에서도 조회·변경할 수 있게 하고 동일한 검증 규칙과 사용자 안내를 사용한다. 정확한 명령 및 설정 키는 구현 설계에서 확정한다.

## 안전 및 복구
- 종료 시각은 새 nullable DB 마이그레이션으로 저장한다. 기존 시각을 추정해 백필하지 않는다. 기존 백업과 DB 버전 정책을 유지한다.
- 수집 잠금 보유 중 분석 잠금은 논블로킹으로 시도하고, 다른 작업 중이면 보류한다. 다른 잠금 순서를 만드는 경로는 교착 분석을 거친다.
- 최신 PR 상태 확인과 실제 삭제 사이 재오픈 가능성을 다룬다. 확인 후 즉시 삭제하되 GitHub 변경과 로컬 삭제의 원자성은 보장되지 않음을 표시한다. 재오픈되면 다음 수집에서 새 스냅샷을 만든다.
- SQLite 트랜잭션으로 레코드를 정리하고 커밋 후 참조 없는 diff를 삭제한다. 중단 후 다음 실행에서 고아 파일을 재정리한다. 경로·소유권 검증을 하고 외부 파일은 삭제하지 않는다.
- SQLite DELETE는 파일 크기 축소나 저장 매체에서의 완전 삭제를 보장하지 않는다. WAL과 DB 여유 페이지, 로컬 백업·OS 백업 사본을 포함한 잔존 범위를 표시한다. 자동 VACUUM이나 OS 백업 삭제는 수행하지 않는다.
- 마이그레이션 및 업데이트 백업은 과거 데이터 복원 시 삭제된 기록이 다시 나타날 수 있음을 안내한다.

## 검증 계획
임시 DB와 파일로 만료 전후, 재오픈·접근 불가, 기존 종료 시각 미확인, 공유 diff, 잠금 경합, 중단 복구, 백업 보존, 경로 검증 및 시간 변경을 확인한다. 설정 UI와 CLI가 같은 정책을 읽고 쓰는지 검증한다. 실제 사용자 DB에 삭제 명령을 실행하지 않는다.

## 결과
- 사용자 요청에 따라 PR 보관 기본 7일, 정리 점검 기본 12시간을 적용했다. 기존 명시 보관 기간은 유지한다.
- 작업 기록 90일, 마지막 기록 후 진단 로그 30일, 백업 수동 삭제를 기본값으로 적용했다.
- 독립 리뷰에서 외부 심볼릭 링크를 통한 삭제, 작업 ID 재사용, 업데이트 중 백업 삭제 오류와 주기적 배치 반복 문제를 수정했다.
- 임시 데이터 기반 수명주기·마이그레이션·설정 검증과 전체 unittest를 실행했다. 실제 사용자 데이터와 GitHub는 사용하지 않았다.
