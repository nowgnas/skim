# macOS 백그라운드 실행

> 상태: 승인됨 · 기준: `0fd57ed` 및 기존 미커밋 변경 · 규모: 표준 · 고위험: 아니오

## 1. 요구사항
- 로그인 사용자 환경에서 skim 웹 서버를 자동 시작하고 비정상 종료 후 재시작한다.
- Dock에서 앱을 열면 기존 서버의 새 일회용 URL로 브라우저에 진입한다.
- 기존 로컬 데이터·CLI 인증·단일 서버 잠금·분석 격리 정책을 유지하고 진입 토큰을 서비스 로그에 남기지 않는다.

## 2. 정책과 맥락
- 사용자는 이전 답변의 LaunchAgent와 Dock 앱 구성을 승인했다.
- `lib/skim/web.py`는 `web.lock` 단일 실행과 0600 `web.sock`을 통해 새 URL을 발급한다. 자동 시작 등록 시 기존 수동 서버와 중복 기동을 처리해야 한다.
- `progress.md:82`의 과거 제거 이력에 따라 서비스 로그 토큰과 잠금 충돌을 피한다.
- 기존 로컬 skim 서버 실행은 `guard-prod-ops` 훅에 차단된 바 있다. 같은 동작을 다른 방식으로 우회하지 않는다.

## 3. 설계
- `skim open`은 실행 중인 서버의 소켓에서 일회용 URL을 받아 브라우저를 열고 URL을 출력하거나 파일에 쓰지 않는다. 서버가 없으면 안내 후 종료한다.
- 사용자별 LaunchAgent는 `skim web --no-browser`를 실행하며 stdout·stderr를 `/dev/null`로 지정한다. 비정상 종료 시에만 재시작해 기존 수동 서버가 있을 때 반복 실행하지 않는다.
- Dock 앱은 `skim open`을 실행하는 작은 AppleScript 앱으로 구성한다. 명령 인수는 명시적으로 이스케이프한다.
- 설치 생성물은 사용자 디렉터리에 명시적으로 설치하며 기존 다른 파일을 덮어쓰지 않는다. 사용자별 PATH, HOME, 필요 시 CODEX_HOME·SKIM_HOME 등 인증 경로 설정을 유지한다. 시크릿은 plist에 저장하지 않는다.
- 기존 수동 서버와 활성 작업을 먼저 확인하며 실행 중 작업을 강제 중단하지 않는다.
- 후속 사용자 요청: 최초 설치와 실행을 `skim app` 한 명령으로 제공한다. 앱과 plist가 같은 skim 설치에서 생성된 것인지 확인해 다른 파일을 덮어쓰지 않고, 이미 실행 중인 수동 서버는 중단하지 않는다. 같은 설치의 반복 실행은 재등록하지 않고 브라우저를 연다.

## 4. 확인 계획
- 구현에 대한 Python 구문, plist 및 diff 확인, 독립 리뷰를 수행한다. 테스트 실행은 사용자 요청이 없어 하지 않는다.
- 환경의 guard-prod-ops 차단을 우회하지 않는다. 서비스 등록 및 기동을 실행하지 못하면 정확한 사유와 사용자 실행 명령을 남긴다.

## 5. 결과
- `skim open`과 사용자 LaunchAgent·Dock 앱 생성기를 구현했다. 진입 URL은 출력하지 않고 서비스 표준 출력과 오류는 `/dev/null`로 보낸다.
- `.design/macos-background/artifacts-v2/`에 준비물을 만들고 `~/Applications/Skim.app`을 설치했다. Dock 고정 및 LaunchAgent 등록·서버 기동은 하지 않았다.
- 기존 서버의 DB 확인 시 실행 중 작업은 없고 수집 하나가 재시도 대기였다. 기존 서버는 유지했다.
- 기존 서버 실행 명령을 `guard-prod-ops`가 차단한 이력이 있어 LaunchAgent를 통해 서버 실행을 우회하지 않았다. 사용자에게 수동 등록 명령을 제공한다.
- `plutil -lint`, Python AST, `git diff --check` 통과. 독립 리뷰에서 상대 경로 문제를 수정하고 재확인했다. 테스트·실제 launchd·브라우저 구동은 하지 않았다.
- `skim app` 명령은 앱과 자동 시작을 설치하고 이후 다시 실행하면 서버를 열도록 구성했다. 수동 서버가 실행 중이면 중단하지 않고 안내한다. 데이터 경로 일치, 기존 설치 소유, launchd PID와 Unix 소켓의 macOS `LOCAL_PEERPID` 일치를 확인한다.
- 명령 자체는 서비스 실행에 대한 기존 `guard-prod-ops` 차단을 우회하지 않도록 실행하지 않았다. 독립 리뷰의 실행 상태 및 경합 지적을 코드에 반영했고 마지막 PID 일치는 정적으로만 확인했다.
