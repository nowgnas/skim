# 조직 팀 저장소 필터

> 상태: 완료 · 기준 커밋: `f3dc671` · 규모: 표준 · 고위험: 아니오

## 1. 요구사항
- 저장소 연결 화면에서 조직 전체에 섞인 목록 대신 내 팀과 관련된 저장소만 볼 수 있는 옵션을 제공한다.
- 기존 전체 조회와 검색·페이지 이동을 유지하고, 목록 조회만으로 저장소를 등록하거나 분석 허용을 변경하지 않는다.

## 2. 정책 점검
- ✅ GitHub 접근은 기존과 같은 읽기 전용 GET, 등록된 호스트 및 공통 백그라운드 큐를 사용한다.
- ⚠️ 기본 제안: 로그인한 사용자가 속한 팀 전체의 저장소를 합쳐 보여주고, 호스트별로 분리한다. 팀을 직접 선택하는 방식은 사용자 답변에 따라 조정한다.
- ✅ GitHub 팀·저장소 조회는 계정 권한과 조직 SSO의 영향을 받는다. 접근 불가나 부분 조회를 전체 결과처럼 표시하지 않고 원인을 안내한다.
- ✅ 조회 실패는 기존 결과를 보존한다. 연결과 분석 동의는 기존 절차를 유지한다.
- ⚠️ 팀/저장소 수가 많을 때 API 요청 상한을 두고 잘린 결과임을 표시한다. 중복 저장소는 한 번만 표시한다.

## 3. 열린 질문
- Q1. 내 소속 팀의 저장소 전체 — 사용자 승인.

## 4. 코드 맥락
- `lib/skim/web_settings.py`: 저장소 조회, 60초 캐시, 목록·폼.
- `lib/skim/jobs.py`: 저장소 조회 큐와 워커.
- `lib/skim/collect.py`: 등록된 GitHub 호스트의 GET, 페이지 및 요청 제한 처리. 기존 수집기는 이미 `user/teams`를 사용한다.
- `tests/test_web_settings.py`, `tests/test_web_jobs.py`: 조회·권한·작업 검증.

## 5. 설계
- GitHub의 `GET /user/teams`와 `GET /orgs/{org}/teams/{team_slug}/repos`를 사용해 현재 사용자의 팀에 연결된 저장소를 조회한다. 조직/팀 식별자를 검증하고 응답의 임의 URL을 실행하지 않는다.
- 기존 전체 조회와 팀 조회의 캐시 키를 구분한다. 서로 다른 호스트 및 조회 조건을 혼동하지 않고, 조회·작업 상태에 현재 조건을 표시한다.
- 실패 시 이전 목록은 보존하되 실패가 사용자에게 보이게 한다. 빈 목록과 부분 목록은 명확히 구분한다.
- 기존 1,000개 상한·백오프를 고려해 팀 수와 API 페이지 호출을 제한하고, 검색·페이지를 기존 구현과 연결한다.
- DB 스키마는 변경하지 않는다.

## 6. 검증 계획
- 전체/팀 모드, 여러 조직·팀, 중복, 권한 실패, 빈 목록, 잘림, 호스트 및 캐시 분리, 중복 작업, 페이지·검색, 비정상 응답을 모의 API로 검증한다.
- 회귀 테스트, 전체 unittest, 독립 리뷰를 수행한다.

## 8. 결과
- 호스트별 전체/내 팀 조회와 조회 모드를 표시한다. 팀 저장소를 중복 제거하고 총 50회 요청·1,000개 제한을 적용한다.
- GitHub SSO 부분 결과와 조회 실패는 실패 상태로 표시하고 이전 결과를 보존한다.
- 독립 리뷰에서 SSO 부분 응답을 완료로 오인할 수 있는 결함을 수정하고 실제 파서 기반 회귀 테스트를 추가했다.
- `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -q`: 259개 통과. 독립 리뷰: SSO 부분 응답 지적을 수정 후 재확인했으며 미해결 중대 지적 없음.
- 사용자 호스트의 GitHub API는 호출하지 않고 모의 응답으로 검증했다.
