# 공개 및 첫 정식 릴리스 준비 작업

이 문서는 공개 저장소와 첫 정식 릴리스를 준비하기 위한 작업 목록이다. 상태는 2026-11-04 원격 `main` 기준의 읽기 전용 조사 결과이며, 각 작업은 담당자가 근거를 남기고 다시 확인한 뒤 완료로 표시한다. 현재는 **공개와 정식 릴리스 모두 준비 중**이다. 공개 전환과 실제 릴리스 발행은 각각 별도의 결정이다.

## 기준과 범위

- 첫 배포는 macOS 사용자 설치 및 웹·CLI 업데이트를 목표로 한다. GitHub의 정식 릴리스만 설치 대상으로 삼는다. 사전 공개 버전을 자동 설치하지 않는다.
- 2026-11-04 기준 저장소는 private이며, GitHub에 정식 릴리스가 없다. 저장소 라이선스가 설정되어 있지 않다.
- 기준 `main`의 분석 프롬프트는 `skim-ko-5`다. `python3 scripts/check_release.py`는 Python 3.11 이상이 필요하며, `/opt/homebrew/bin/python3 scripts/check_release.py` 실행 시 `confirmed_by` 누락으로 실패했다.
- [이전 릴리스 검토](pre-release-review-2026-11-04.md)는 당시 미커밋 `skim-ko-6` 변경을 포함한 기록이다. 해당 변경의 반영 여부와 후보 버전은 릴리스 후보에서 다시 확정한다.
- 개인 로컬에 남은 미커밋 변경은 릴리스 후보에 자동 포함되지 않는다. 개별 변경을 리뷰하고 머지한 뒤 후보 커밋을 고정한다.

## 우선순위와 완료 조건

### P0-1. 공개 가능 범위와 권리 확인

- [ ] 소유자와 기여자의 공개 권한을 확인하고 프로젝트 및 제3자 코드·의존성의 라이선스를 검토한다. 사용할 라이선스를 결정해 `LICENSE`를 추가하고, 선택한 조건에 따라 배포 아카이브에 라이선스와 필요한 고지문이 포함되는지 확인한다.
- [ ] 현재 파일뿐 아니라 Git 전체 이력, 브랜치·태그, PR·이슈와 첨부, Actions 로그·아티팩트, 릴리스 자산의 공개 가능성을 조사한다. 비밀정보, 사내 코드·PR diff, 식별자, 개인 정보와 내부 URL을 검토한다. 스크린샷과 `eval/`의 입력·결과·확인자 정보도 포함한다.
- [ ] 점검 범위, 책임자, 결과와 미확인 항목을 남긴다. 문제가 있으면 제거·권한 조정과 필요한 자격 증명 폐기를 먼저 처리한다. 기존 이력과 기록을 공개하기 어렵다면 별도 공개 저장소 사용을 결정한다.
- [ ] 취약점의 비공개 제보 방법과 대응 경로를 정해 공개 문서에 기록한다.

**완료 기준:** 공개 대상 전체의 검토 근거와 권리 확인이 있고, 잔여 위험 및 공개 저장소 방식에 대한 소유자 결정이 기록되어 있다. 아직 전체 이력이나 외부 기록의 공개 안전성은 검증하지 않았다.

### P0-2. 설치·업데이트·복구 구현

- [ ] 최초 설치 bootstrap과 사용자 전용 영구 launcher를 완성하고 배포물 생성이 요구하는 설치 자산을 제공한다. 현재 `lib/skim/release_package.py`가 요구하는 `lib/skim/bootstrap.py`는 없다.
- [ ] 정식 릴리스 조회뿐 아니라 CLI와 웹 설정에서 업데이트 적용, 상태 표시, 재시작과 readiness 확인을 연결한다. 현재 `skim update`는 조회 후 자동 적용이 준비 중이라고 안내한다.
- [ ] 수집·분석과 설정 쓰기 등 모든 진입점에서 유지보수 경계를 지키고, 진행 중인 작업을 기다린 뒤 전환한다. 별도 관리자와 journal로 강제 종료, 재시도, 전환·재시작 실패를 복구한다.
- [ ] SQLite 백업과 버전·마이그레이션 호환성을 확인하고, 쓰기가 시작된 이후의 안전하지 않은 자동 롤백을 막는다. 기존 개발 checkout, 다른 설치, 사용자의 데이터 및 인증을 보존한다.
- [ ] 공개 저장소로 전환할 경우 기존 설계의 private 저장소 및 `gh` 인증 가정을 재검토하고, 현재 구현은 `gh` 토큰과 `nowgnas/skim` 주소를 전제로 하므로 공개 자산의 비인증 접근, GitHub API 제한 및 인증 필요 오류를 구분한다. 별도 공개 저장소를 택하면 릴리스 출처 계약도 함께 변경한다.

**완료 기준:** 격리된 설치 환경에서 정상 설치·업데이트, 작업 중 대기, 중복 요청, 다운로드 오류, 강제 종료, 재시작·복구 및 데이터 보존을 확인하고 [.design/install-update/GATES.md](../.design/install-update/GATES.md)의 해당 게이트와 독립 리뷰를 완료한다. 현재 구현 상태와 상세 설계는 [설치·업데이트 계획](../.design/install-update/PLAN.md)을 따른다.

### P0-3. 분석 품질과 출시 게이트

- [ ] 릴리스 후보의 프롬프트·스키마·모델 버전을 고정하고, 해당 버전의 평가 사례와 기대 파일을 사람이 확인한다. 다른 버전의 결과를 그대로 재사용하지 않는다.
- [ ] 실제 모델로 평가하고 요청·결과·원본 출력과 민감 정보 정제 결과를 사람이 검토한다. 지정된 중요 파일 누락과 미분석 내용 숨김을 확인한다.
- [ ] 새 테스트 중요도 정책을 후보에 포함한다면 테스트 중심 PR, 검증 약화, 대응 테스트, 공통 fixture, 핵심 UI, 정보 부족 사례를 추가한다. 모델 중요도 판정과 규칙 후보 포착을 구분해 판단하고 자동 게이트의 필수 조건에도 반영한다.
- [ ] 목적 요약과 먼저 볼 파일의 품질은 같은 모델·CLI·확인된 정답을 사용한 반복 비교와 사람 검토로 판단한다. 캐시 버전 분리와 증거 분리도 별도로 확인한다.

**완료 기준:** [출시 체크리스트](release-checklist.md)에 따라 후보 커밋에서 `scripts/check_release.py`가 통과하고, 평가 자료와 사람 검토 근거가 보존된다. 후보 SHA와 함께 프롬프트·스키마·입력 diff·모델·CLI 버전 및 평가 결과의 해시를 기록하고, 작업 트리 평가 입력과 배포 코드가 후보와 일치함을 확인한다. 평가 자료 공개 가능성은 P0-1에서 별도로 결정하며 공개할 수 없는 증거의 접근 통제 위치와 검증 방법을 기록한다.

### P0-4. 제품 흐름과 릴리스 후보 검증

- [ ] 포함할 미커밋 변경을 개별적으로 정리·검토하고, 단일 후보 커밋과 정확한 코드·설치 자산·문서 버전을 확정한다.
- [ ] 깨끗한 환경에서 설치 → 인증 → 저장소 연결·분석 허용 → PR 수집 → 수동·자동 분석 → 리뷰 상세 → 업데이트 흐름을 확인한다. 오류·권한 부족·빈 결과와 복구 경로도 포함한다.
- [ ] PR 상세의 파일 검색 및 탐색을 파일 다수·페이지 경계·키보드·모바일 화면에서 확인한다. 함수 탐색을 후보에 포함한다면 프로젝트 함수와 표준 라이브러리 구분 및 위치 복귀도 확인한다.
- [ ] 후보 커밋의 CI, 주요 플랫폼·지원 버전 검증, 설치·분석 게이트 및 독립 리뷰의 차단 사항을 해결한다. 결과와 남은 제약을 후보 SHA에 연결한다.

**완료 기준:** 후보 SHA에 대한 확인 결과와 독립 리뷰가 기록되고 차단 사항이 모두 해결되어 있다. CI 통과만으로 실제 모델 평가나 브라우저·설치 검증을 대신하지 않는다.

### P1. 공개 사용자를 위한 문서와 운영

- [ ] README에 지원 OS·Python·GitHub/Codex 요구 사항, 설치·제거·업데이트, 첫 실행, 비용·호출 제한, 오류 해결을 현재 구현과 일치하게 작성한다.
- [ ] 저장 위치, GitHub 권한과 SSO, 모델 서비스로 전송되는 정보 및 정제의 한계, 데이터 삭제·백업 방법을 설명한다.
- [ ] 변경 이력, 기여·이슈 접수 방법, 취약점 비공개 제보와 유지보수 범위를 안내한다. 예제와 이미지가 공개 가능하고 재현 가능한지 확인한다.
- [ ] 릴리스 자산·체크섬·태그와 릴리스 노트 작성 절차, 게시 실패 대응 및 배포 후 점검 절차를 정리한다. 체크섬은 전송 오류 확인이며 출처 서명을 대신하지 않는다.

## 진행 순서와 의존 관계

1. P0-1 공개 범위 확인과 P0-2 설치 설계를 병행한다. 권리·정보 노출 문제는 공개 전 반드시 해결한다.
2. P0-2 구현과 P0-3 평가 준비를 병행한다. 평가 대상 버전과 코드가 바뀌면 후보를 다시 고정하고 필요한 평가를 재실행한다.
3. P1 문서를 실제 지원 범위에 맞춰 완성하고 P0-4에서 확정된 후보 전체를 검증한다.
4. 모든 P0 완료 근거와 P1 문서를 검토한 뒤 저장소 공개 여부를 결정한다. 공개 전환 자체는 이 문서 작성으로 수행하지 않는다.
5. 공개된 배포 경로와 후보 자산을 다시 확인하고 정식 릴리스 발행을 결정한다. 발행 후에는 게시된 자산의 체크섬을 독립적으로 확인하고 최소 설치·실행을 점검한다. 배포 이상 시 공지 및 릴리스 중단·복구 절차를 따른다. 정식 릴리스 발행 역시 별도 작업이다.

## 현재 결정이 필요한 항목

- 프로젝트 라이선스 및 기여 코드의 권리 확인 담당자.
- 기존 저장소와 전체 이력을 공개할지, 검토된 내용으로 별도 공개 저장소를 만들지.
- 첫 정식 릴리스에 포함할 로컬 미커밋 기능과 지원 macOS 범위.
- 취약점 제보 창구와 릴리스·업데이트 유지보수 담당자.
